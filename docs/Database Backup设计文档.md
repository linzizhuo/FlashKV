DB（Database Backup）​ 是一种持久化机制，它在指定的时间间隔内，将内存中的整个数据集生成一个二进制压缩文件（dump.fdb），保存到磁盘中。
在本项目中本质是将hash表中的数据写入文件中。核心是对数据结构的二进制编码。


关键设计：
    全量复制，不是增量，不是追加。每次 BGSAVE 把整个数据集序列化成一个 dump.rdb 文件
    并发：fork创建子进程，父进程继续工作，子进程复制。（因为现代计算机的磁盘都是脱手操作（靠隔离，中断等机制实现），所以这种方法不会对主进程产生很大影响（猜测）。）
问题：
    父进程和子进程共享内存页，那么共享区怎么处理？
        核心依据——为什么RDB可行：COW（Copy-On-Write，写时复制）​，只读共享，修改分离，甜菜！

那么RDB的流程就很明显了：
    写过程——开始Backup，遍历db，将数据结构转换成二进制数据，写入临时文件，原子替换
    恢复过程——读一遍，然后依次插入数据库中（懒汉实现，可以做对应的优化）
支持命令：
SAVE 阻塞写入
BGSAVE 非阻塞写入

rdb文件格式
┌──────────────────────────────────────┐
│ 魔数 "FLASHKV" (7 bytes)             │  文件头
│ 版本号  (4 bytes)                     │
├──────────────────────────────────────┤
│ 1B: type (0=STRING,1=INT,2=ZSET)     │
│ 4B: key_len + key 数据               │
│ 4B: val_len + value 数据             │  数据体（循环）
│ 8B: expire_time (0=无过期)           │
│ ... 更多 key-value ...               │
├──────────────────────────────────────┤
│ CRC64 (8 bytes)                      │  文件尾
└──────────────────────────────────────┘
sds类型很简单，char都是1字节，直接写入就可以
int类型也很简单，固定long long八个字节，也可以直接写入
TTL的数据每一个节点后跟一个8字节的过期时间戳（type的最高位做标记）
zset需要额外设计一下。


代码方案：
    最开始考虑函数回调，最后发现从kvdb到最后底层有好几层封装，回调的话要函数调来调去，而且函数回调复用性也不高，所以舍弃了这种方案，选择迭代器的方式进行dict遍历。C++的STL也是选择的迭代器。因为对STL的设计比较熟悉，所以在命名上也就更倾向于STL的方案。
