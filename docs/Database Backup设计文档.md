DB（Database Backup）​ 是一种持久化机制，它在指定的时间间隔内，将内存中的整个数据集生成一个二进制压缩文件（dump.fdb），保存到磁盘中。
在本项目中本质是将hash表中的数据写入文件中。核心是对数据结构的二进制编码。


关键设计：
    全量复制，不是增量，不是追加。每次 BGSAVE 把整个数据集序列化成一个 dump.rdb 文件
    并发：fork创建子进程，父进程继续工作，子进程复制。（因为现代计算机的磁盘都是脱手操作（靠隔离，中断等机制实现），所以这种方法不会对主进程产生很大影响（猜测）。）
问题：
    父进程和子进程共享内存页，那么共享区怎么处理？
        核心依据——为什么RDB可行：COW（Copy-On-Write，写时复制）​，只读共享，修改分离，甜菜！

那么RDB的流程就很明显了：
    写过程——开始Backup，遍历db，将数据结构转换成二进制数据，写入临时文件，原子替换
    恢复过程——读一遍，然后依次插入数据库中（懒汉实现，可以做对应的优化）
支持命令：
SAVE 阻塞写入
BGSAVE 非阻塞写入

rdb文件格式
┌──────────────────────────────────────┐
│ 魔数 "FLASHKV" (7 bytes)             │  文件头
│ 版本号  (4 bytes)                     │
├──────────────────────────────────────┤
│ 1B: type (0=STRING,1=INT,2=ZSET)     │
│ 4B: key_len + key 数据               │
│ 4B: val_len + value 数据             │  数据体（循环）
│ 8B: expire_time (0=无过期)           │
│ ... 更多 key-value ...               │
├──────────────────────────────────────┤
│ CRC64 (8 bytes)                      │  文件尾
└──────────────────────────────────────┘
sds类型很简单，char都是1字节，直接写入就可以
int类型也很简单，固定long long八个字节，也可以直接写入
TTL的数据每一个节点后跟一个8字节的过期时间戳（type的最高位做标记）
zset需要额外设计一下。


代码方案：
    最开始考虑函数回调，最后发现从kvdb到最后底层有好几层封装，回调的话要函数调来调去，而且函数回调复用性也不高，所以舍弃了这种方案，选择迭代器的方式进行dict遍历。C++的STL也是选择的迭代器。因为对STL的设计比较熟悉，所以在命名上也就更倾向于STL的方案。
rdb是kvdb内部的功能，但又要做到对kvdb的内部数据无感知……


zset序列化：遍历 skiplist 把 (score, member) 逐条 dump，反序列化时逐条 zsetAdd 回去。顺序插入写起来最简单，代价是反序列化时重建索引慢一些——够用再说。丐版实现，后面可以优化，一次来回实现反序列化。

跳表
double score;                   // 排序分值
sds ele;                        // 元素（动态字符串）
没有key-val之分
score有8个字节，ele是动态的，所以格式应该是
8B: score + sds

通用的 [4B val_len][data] 对 zset 这种可能很大的结构确实有问题——你必须先把整个 zset 序列化到一块 malloc 缓冲区才能知道 val_len，极端情况下（百万级 member）这会导致巨大的临时内存占用。
类型特化，各自自描述（实际上val_len也是属于序列内部的，所以这样讲没问题）

                    每种类型自己负责"读到哪里算结束"

但问题随之而来，序列化接口是一次输出一个buf，这个buf可能很大，而且某些特殊的数据结构还需要O(n)遍历两次，这显然造成了极大的浪费。
所以我选择设计专门的output接口，将序列化和写入文件解耦，设计一个结构体为缓冲区，序列化只需要调用add就可以不断追加到缓冲区末尾，
而add内部会在缓冲区满时调用io写入磁盘中。
这样做的好处一是让序列化不会特别臃肿，二是方便了后面扩展
（其实这个缓冲区可以直接使用文件IO的，自带缓冲区，但我想要每个节点独立写入，不想写入半个这种情况，所以决定自己写缓冲区（其实未必有缓冲区））
所以要对dict和跳表这种结构配置流式接口？感觉有些似曾相识，之前为了在外层迭代dict所以编写了迭代器，对于dict来说写入的粒度的一个节点
跳表也可以学习这种思想，配置迭代器，对每个节点序列化，支持流式写入。


写入磁盘策略
最开始思路是写序列化函数，每次从序列化中获取buf，随后再写入磁盘。
但是发现这样会有很多的内存碎片，海量malloc，这显然很影响速度。
想要优化，需要让多个对象共享buf，为了实现这一功能。
我选择抽取出专门的IO层，底层使用标准IO写入文件，高层管理缓冲区，缓冲区分为两部分。
1.输入队列，会在特定时机刷新写入磁盘，这点借鉴文件IO
2.输入缓冲区，这部分是共享buf的关键，每次写入时getbuf，随后再add进buf。
这样我们便省去了大量的malloc，也间接控制了磁盘IO(省掉大量的扫盘消耗)，也控制了内存，不会出现buf太大的情况。
内存结构设计：
int fd   文件按控制符
char* buf1, buf2; // 灵活控制写入数组和buf，这样有一个优点：可以在add的时候省去很多的数组复制，算是一个小优化，如果想继续优化的话可以使用消息队列+链表的格式（链表就提前分配），每次只限定l+r，这样io的时候可以动态……当然这显然过于复杂了，为了省去一次O(n)这样显得有些本末倒置。比较瓶颈还是磁盘io
int len; //缓冲区大小
char buf[doublesize] //柔性数组，再省去一次malloc，虽然文件io的使用场景在本项目中并不多，只算是一个小优化。
