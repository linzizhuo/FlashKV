这期主要是解析Redis网络层的设计思路，以及辩证的看待选择的优略。

1. 为什么Redis选择TCP协议？
    TCP的适用场景是长连接、大数据、数据可靠性要求高。Redis完全符合这三个场景。
    但TCP本身也有缺点，数据实时性差，短连接不友好——这也是HTTP/3舍弃TCP的原因。
2. 为什么说在应用层视角来看 TCP 是"异步"的

这是反常识的一个点。TCP 在传输层是同步的——确认帧、重传机制、滑动窗口、
拥塞控制，教材里明摆着写着 TCP 是同步可靠的。那为什么说应用层视角下它是"异步"的？

答案在于系统调用语义。

当我们调用 send() 时，它只承诺"数据拷进内核发送缓冲区了"，不承诺"数据发出去了"。
什么时候真正发、分几个包发、重不重传，全是内核 TCP 栈说了算——应用层完全不知情。
这就是异步：你把活交给内核，它什么时候干完不告诉你。

反过来，接收端的 recv() 也一样：数据什么时候到、分几次到、一次 recv 能拿多少，
全不归你管。

更麻烦的是，TCP 是字节流，不保留消息边界。你发三次 "hello"，对端可能一次 recv
拿到 "hellohellohello"——这就是粘包；也可能一次只拿到 "hel"——这就是拆包。
你需要一个应用协议来界定消息边界。

常见的应用层消息界定格式有哪些：

1. 分隔符界定：用一个或多个特殊字节标记消息结尾。
2. 前置长度：在消息体之前，用固定字节的 header 声明消息长度。
3. 固定长度：所有消息具有完全相同的字节数。

分隔符界定优点：简单，可读性好，缺点：不适用于二进制。
前置长度优点：简单，缺点：长数据要知道长度。
固定长度优点：简单，缺点：字节很难利用到位。

RESP格式

首字节	类型	格式	示例
+	Simple String	+<文本>\r\n	+OK\r\n
-	Error	-<错误信息>\r\n	-ERR unknown command\r\n
:	Integer	:<数字>\r\n	:1000\r\n
$	Bulk String	$<长度>\r\n<数据>\r\n	$5\r\nhello\r\n
*	Array	*<元素数>\r\n<元素1>...<元素N>	*2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n

首字符用来界定格式
对于短文本场景，\r\n分隔符足够简介，一次界定边界的消耗几乎忽略不计，也不会有二进制问题
而对于二进制串，使用前置长度，简单，适合长串。

为什么epoll适合高并发场景，epoll和select/poll的区别是什么？

首先先说一下epoll是什么——io多路复用机制在网络层的实现。

为什么需要epoll?这个问题应该从select/poll有什么缺陷引入

while (1)
    FD_ZERO + FD_SET 注册所有 fd
    select(maxfd+1, &rfds, NULL, NULL, NULL)
    for 每个 fd
        if FD_ISSET(fd)
            处理

有一个显而易见的缺陷：每次select返回后，服务端都需要遍历所有的fd，才能确定哪些fd收到了消息，这是一种很笨的方法……

epoll是如何规避的？答案是事件驱动的设计思想。

epoll相比于select，他不会让你去主动遍历寻找，而是会直接告诉你哪些fd触发了中断。

原理：
    红黑树 + 就绪链表 + 回调驱动。

epoll fd 内部：
  ┌─ 红黑树 (rbtree) ──────── 存所有注册的 fd，key = fd
  └─ 就绪链表 (rdllist) ───── 存就绪的 fd，epoll_wait 直接从这里取


网卡中断发生后，Linux内核除了将数据放入缓冲区之外，还会调用ep_poll_callback()回调函数，将fd丢进rdllist。

这个思想和设计模式中的观察者模式很像。本质是同一设计思想。

水平触发和边沿触发，redis为什么选择水平触发：
    我觉得这个问题很简单也很……我觉得水平触发最大的优势就是实现简单，而且适合现在的数据流的格式，最重要的是遇到半包不会阻塞。

    而边沿触发遇到半包是会阻塞的，对于redis这种单线程模型来说，任何一个阻塞都是致命的，redis在其他地方的设计也可以看出它在主动规避阻塞——网络层使用事件驱动，水平触发，持久化使用fork+cow写时复制，读写使用单线程避免锁争夺开销，redis的日志选择使用重定向符异步写入，甚至对惰性删除随机抽样这种定时操作都不会交给中断驱动，而是在主循环中顺手就做了。

    所以水平触发的好处可能就是实现简单 + 避免阻塞。
